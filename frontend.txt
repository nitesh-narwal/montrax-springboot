## What's new since the last frontend build (read this first, in plain language)

- **Sign-up now needs a phone number.** After registering, the user must enter an
  SMS OTP code before they're allowed to log in. Build an OTP-entry screen. See
  section 4.1 (`POST /register`, `POST /api/otp/verify`).
- **"Sign in with Google" is available.** It's a page redirect, not a normal API
  call — see "Google Sign-In (OAuth2)" in section 4.1.
- **Some users are admins now.** A logged-in admin can see a `/api/admin/**`
  panel (user list, role management, system stats, config editor). Regular users
  never see this. See sections 3.9 and 4.17.
- **Big lists are paginated.** Expense/income history and filtered search now have
  `/paged` endpoint variants that return `{ content, currentPage, totalPages, ... }`
  instead of a raw array. Use these for any table/list UI. See section 4.16.
- **The API can rate-limit you (HTTP 429)** and **supports safe retries via an
  `X-Idempotency-Key` header.** Both are just things your HTTP client layer should
  handle generically — see sections 3.7 and 3.8.
- **Emails now send in the background** (via a queue) instead of blocking the
  request — no frontend change needed, requests just return faster.
- **The database is PostgreSQL** — none of this affects the frontend either way,
  the API contracts below are the same regardless of what's behind them.

# 1. System Overview

## 1.1 What This System Does

### Simple Terms
Money Manager is a personal finance tracking application that helps users:
- Track daily income and expenses
- Set and monitor budgets per category
- Import bank statements (CSV)
- Get AI-powered financial insights
- Receive automated reminders for recurring payments
- View analytics and spending trends
- Sign up with phone OTP verification, or sign in instantly with Google
- (Admins only) manage users and system settings from an admin panel

### Technical Terms
A multi-tier Spring Boot REST API application featuring:
- JWT-based stateless authentication, with Google OAuth2 as an alternative login method
- Role-based access control (USER / ADMIN)
- Multi-database architecture (PostgreSQL + MongoDB + Redis)
- AI integration via Google Gemini API
- Payment gateway integration (Razorpay)
- SMS OTP verification via Twilio
- Async processing via RabbitMQ (emails) and Kafka (transaction/audit event streaming)
- Per-user, per-tier rate limiting and idempotent request handling
- Scheduled background jobs for automation
- Subscription-based feature gating with AOP

## 1.3 Request-Response Flow

```
┌─────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ Client  │────▶│ JWT Filter  │────▶│ Controller  │────▶│  Service    │
└─────────┘     └─────────────┘     └─────────────┘     └─────────────┘
                      │                    │                   │
                      │ Validate           │ Parse             │ Business
                      │ Token              │ Request           │ Logic
                      ▼                    ▼                   ▼
               ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
               │  Security   │     │ Premium     │     │ Repository  │
               │  Context    │     │ Aspect      │     │  Layer      │
               └─────────────┘     └─────────────┘     └─────────────┘
                                                              │
                                                              ▼
                                                       ┌─────────────┐
                                                       │  Database   │
                                                       └─────────────┘
```


**Step-by-Step Flow:**

1. **Request Arrives** → Client sends HTTP request with JWT in `Authorization` header
2. **JWT Filter** → `JwtRequestFilter` extracts and validates token
3. **Security Context** → User principal is set in `SecurityContextHolder`
4. **Controller** → Receives request, validates input
5. **Premium Aspect** → `@PremiumFeature` checks subscription level
6. **Service Layer** → Executes business logic
7. **Repository** → Performs database operations
8. **Response** → JSON response returned to client

## 3.2 JWT Token Structure

```
Header:
{
  "alg": "HS256",
  "typ": "JWT"
}

Payload:
{
  "sub": "user@email.com",    // User email (subject)
  "iat": 1713456789,          // Issued at timestamp
  "exp": 1713543189           // Expiration timestamp
}

Signature:
HMACSHA256(base64(header) + "." + base64(payload), SECRET_KEY)
```

## 3.6 Security Best Practices Implemented

| Practice | Implementation |
|----------|---------------|
| Password Hashing | BCrypt (strength factor default) |
| Stateless Auth | JWT tokens, no server sessions |
| CORS Configuration | Whitelist specific origins |
| CSRF Protection | Disabled (stateless API) |
| Token Expiration | Configurable via `jwt.expiration` |
| Rate Limiting | Per-user, per-hour, tier-based (see 3.7) |
| Idempotency | `X-Idempotency-Key` header (see 3.8) |
| Input Validation | DTO validation + service checks |
| SQL Injection | Spring Data JPA parameterized queries |

## 3.7 Rate Limiting (applies to every authenticated endpoint)

```
Every JWT-authenticated request counts against the user's hourly quota, based on
their subscription tier:
  FREE = 100 requests/hour, BASIC = 500/hour, PREMIUM = 2000/hour, ADMIN = unlimited

When the limit is exceeded, backend returns:

Response (429 Too Many Requests):
{
  "message": "Rate limit exceeded. Try again later.",
  ...
}
Header: Retry-After: 3600

FRONTEND TODO: add a global fetch/axios interceptor that catches 429s and shows a
"You're doing that too much, try again in a bit" toast using the Retry-After header
(seconds) to tell the user roughly when to retry. Don't auto-retry in a loop.
```

## 3.8 Idempotency (optional, use for POST/PUT that create/charge something)

```
Send an `X-Idempotency-Key` header (any unique string you generate, e.g. crypto.randomUUID())
on a POST/PUT and the backend caches the response for 24 hours. If the exact same request is
sent again with the same key (e.g. user double-clicks "Pay" or a retry fires after a flaky
network), the backend replays the ORIGINAL response instead of doing the action twice.

FRONTEND TODO: generate a fresh UUID per "logical action" (e.g. once when a payment form is
opened) and reuse it if you retry that same submission — not a new UUID per retry.
Most useful on: POST /api/payments/create-order, POST /expences, POST /incomes.
```

## 3.9 Roles & Admin Panel

```
Every profile has a role: "USER" (default) or "ADMIN". The JWT now carries the role as a
claim. Admin-only endpoints live under /api/admin/** and return 403 for non-admins.
There's no self-serve way to become admin — the first admin account is seeded from
server-side env vars on startup. Frontend should hide any admin UI unless
user.role === "ADMIN" (from the /login or /profile response).
```

# 4. API Endpoints

## 4.1 Authentication Endpoints

### POST /register
**Creates a new user account. Phone number + OTP verification is now REQUIRED — a user cannot log in until they verify the OTP sent to their phone.**

```
Request:
{
  "fullname": "John Doe",
  "email": "john@example.com",
  "password": "securePassword123",
  "phoneNumber": "+919876543210"
}

Response (201 Created):
{
  "id": 1,
  "fullname": "John Doe",
  "email": "john@example.com",
  "profileImageUrl": null,
  "role": "USER",
  "phoneNumber": "+919876543210",
  "isPhoneVerified": false,
  "authProvider": "LOCAL",
  "createdAt": "2026-04-18T10:30:00",
  "updatedAt": "2026-04-18T10:30:00"
}

Validation Rules:
- email: Required, valid email format, unique
- password: Required, min 8 characters recommended
- fullname: Required
- phoneNumber: Required (E.164 format recommended, e.g. +919876543210) — registration fails without it

Internal Flow:
1. Check if email already exists → throw if duplicate
2. Require phoneNumber → throw if missing/blank
3. Hash password with BCrypt
4. Generate UUID activation token, save profile with isActive=false, isPhoneVerified=false
5. Send activation email asynchronously (via RabbitMQ, doesn't block the response)
6. Send a 6-digit OTP by SMS to phoneNumber (Twilio) — best-effort, user can resend via /api/otp/resend
7. Return profile DTO (without password)

FRONTEND FLOW: after register succeeds, immediately show an "enter the OTP we texted you" screen,
call POST /api/otp/verify, THEN let the user log in. Login will be rejected with 403 until this is done.
See "OTP Verification Endpoints" below.
```


### POST /login
**Authenticates user and returns JWT. Blocked with 403 until the phone number is OTP-verified.**

```
Request:
{
  "email": "john@example.com",
  "password": "securePassword123"
}

Response (200 OK):
{
  "token": "eyJhbGciOiJIUzI1NiJ9...",
  "user": {
    "id": 1,
    "fullname": "John Doe",
    "email": "john@example.com",
    "profileImageUrl": "https://cloudinary.com/...",
    "role": "USER",
    "phoneNumber": "+919876543210",
    "isPhoneVerified": true,
    "authProvider": "LOCAL",
    "createdAt": "2026-04-18T10:30:00",
    "updatedAt": "2026-04-18T10:30:00"
  }
}

Response (401 Unauthorized):
{
  "message": "Invalid email or password"
}

Response (403 Forbidden) - account not activated (email link not clicked):
{
  "message": "Account is not activated."
}

Response (403 Forbidden) - phone not OTP-verified yet:
"Phone verification required. Please verify the OTP sent to your phone before logging in."

Status Codes:
- 200: Success
- 401: Invalid credentials
- 403: Account not activated OR phone not verified (check the message body to tell them apart)

Internal Flow:
1. Check if account has pending deletion → cancel deletion if login succeeds
2. Check isPhoneVerified → reject with 403 if false (checked BEFORE password auth)
3. Authenticate via AuthenticationManager
4. Check if account is active
5. Generate JWT token — now embeds a "role" claim (USER/ADMIN) alongside the email subject
6. Return token + user profile (includes role/phoneNumber/isPhoneVerified/authProvider)

IMPORTANT for frontend: every JSON POST/PUT request can optionally carry an
`X-Idempotency-Key` header (any unique string, e.g. a UUID you generate client-side)
to make retries safe — see "Idempotency" in section 3. And watch for HTTP 429
responses on ANY endpoint — see "Rate Limiting" in section 3 — they mean the user's
plan-tier hourly limit was hit; show the `Retry-After` header value to the user.
```


### Google Sign-In (OAuth2) — alternative to email/password login

```
This is a browser REDIRECT flow, not a JSON API call — do not fetch() it, navigate the browser to it.

1. Frontend redirects the whole page to:
     GET {backend-base-url}/oauth2/authorization/google
2. Backend sends the browser to Google's consent screen, user approves.
3. Google redirects back to the backend, which creates the profile if it's a first-time
   Google user (isActive=true, isPhoneVerified=true automatically — Google already verified
   the person, so no OTP step for Google accounts) or matches an existing profile by email.
4. Backend issues the SAME kind of JWT as POST /login, then redirects the browser to:
     {frontend-url}/oauth2/redirect?token=eyJhbGciOiJIUzI1NiJ9...
5. Frontend's /oauth2/redirect route reads the `token` query param, stores it exactly like
   a normal login token, then calls GET /profile (or similar) to fetch the user object.
6. On failure, backend redirects to {frontend-url}/login?error=<message> instead.

FRONTEND TODO: add a "Sign in with Google" button that does
`window.location.href = \`${BACKEND_URL}/oauth2/authorization/google\`` and a
`/oauth2/redirect` route that extracts `?token=` and finishes login client-side.

A profile created via Google login has authProvider="GOOGLE" and no password —
don't show a "change password" option for those accounts unless you also add a
"set a password" flow (not implemented on the backend).
```

## 4.15 Filter Endpoint

### POST /filter
**Filters transactions by criteria**

```
Request:

  "startDate": "2026-01-01",
  "endDate": "2026-04-18",

[
  {
    "id": 42,
    "name": "Grocery Shopping",
    "amount": 1500.00,
    ...
  }
]
```

### POST /filter/paged
Same request body as above, but also takes standard pagination query params
(`page`, `size`, `sort`) and returns a `PagedResponse` instead of a raw array —
see "Pagination" note under 4.16 for the exact response shape. Use this one for
any UI with more than ~50 transactions; the plain /filter endpoint returns everything
at once and doesn't scale.

## 4.17 Admin Endpoints (require role=ADMIN — see 3.9)

```
GET /api/admin/users?page=0&size=20&search=john

  Request: { "role": "ADMIN" }   // or "USER"

  Request: { "value": "new-value" }
  → Read/write server-side runtime config (things like the frontend URL used in
```

# 6. Analytics & Insights

## 6.1 Spending Analysis Explanation

The system provides comprehensive spending analysis through multiple dimensions:

### Category-wise Breakdown
```
How it's calculated:
1. Fetch all expenses in date range
2. Group by category name
3. Sum amounts per category
4. Sort by amount descending

Frontend Chart: Pie/Donut Chart
- Each slice represents a category
- Size proportional to spending
- Colors: Use distinct colors per category
```


### Daily Spending Trends
```
How it's calculated:
1. Fetch expenses in date range
2. Group by date
3. Fill missing dates with 0
4. Return as array of {date, amount}

Frontend Chart: Line Chart / Area Chart
- X-axis: Dates
- Y-axis: Amount in ₹
- Line shows spending trend
```


### Monthly Comparison
```
How it's calculated:
1. Fetch expenses/incomes for each month
2. Calculate total per month
3. Return as array of {month, income, expense, savings}

Frontend Chart: Bar Chart (grouped)
- X-axis: Month names (Jan, Feb, etc.)
- Y-axis: Amount in ₹
- 3 bars per month: Income (green), Expense (red), Savings (blue)
```


## 6.2 Key Metrics Calculation

| Metric | Formula | Description |
|--------|---------|-------------|
| Balance | Income - Expense | Net financial position |
| Savings Rate | (Savings ÷ Income) × 100 | % of income saved |
| Daily Average | Total ÷ Days | Average daily spending |
| Projected Total | Daily Average × Days in Month | Expected month total |
| Budget Usage | (Spent ÷ Budget) × 100 | % of budget used |

## 6.3 AI Insights Types

### SPENDING_ANALYSIS
- Analyzes spending patterns
- Identifies top categories
- Suggests optimization areas
- Priority: Based on savings rate

### SAVINGS_STRATEGY
- Personalized savings plan
- Target setting recommendations
- Step-by-step action items
- Emergency fund advice

### FINANCIAL_HEALTH
- Overall health score (0-100)
- Component breakdowns
- Areas for improvement
- Positive highlights

# 8. Error Handling & Edge Cases

## 8.1 Standard Error Response Format

```json
{
  "success": false,
  "message": "Human-readable error message"
}
```


For validation errors:
```json
{
  "error": "Validation failed",
  "message": "Detailed description",
  "field": "fieldName"  // Optional
}
```


## 8.2 HTTP Status Codes

| Code | Meaning | When Used |
|------|---------|-----------|
| 200 | OK | Successful GET, PUT, POST |
| 201 | Created | Resource created (POST) |
| 204 | No Content | Successful DELETE |
| 400 | Bad Request | Validation error, invalid input |
| 401 | Unauthorized | Invalid/missing JWT |
| 403 | Forbidden | Premium feature access denied |
| 404 | Not Found | Resource doesn't exist |
| 500 | Server Error | Unexpected error |

## 8.3 Common Edge Cases

### Invalid Inputs
```
Scenario: Empty required field
Response: 400 Bad Request
{
  "error": "Validation failed",
  "message": "Field 'name' is required"
}

Scenario: Invalid date format
Response: 400 Bad Request
{
  "message": "Invalid date format. Use yyyy-MM-dd"
}

Scenario: Negative amount
Response: 400 Bad Request
{
  "message": "Amount must be positive"
}
```


### Missing Data
```
Scenario: Category not found
Response: 404 Not Found
{
  "message": "Category not found with id: 999"
}

Scenario: Transaction not found
Response: 404 Not Found
{
  "message": "Expense not found with id: 999"
}
```


### Permission Denied
```
Scenario: Access other user's data
Response: 403 Forbidden
{
  "message": "You don't have permission to delete this expense"
}

Scenario: Premium feature without subscription
Response: 403 Forbidden
{
  "message": "This feature requires a BASIC or PREMIUM subscription. Please upgrade to access: AI Analysis"
}
```


### Rate Limits
```
Scenario: AI query limit exceeded
Response: 429 or custom error
{
  "message": "AI query limit reached for this month (5/5). Please upgrade to PREMIUM for more queries or wait until next month."
}

Scenario: CSV import limit exceeded
Response: 403 Forbidden
{
  "message": "Monthly CSV import limit reached (3/3). Please upgrade to PREMIUM for unlimited imports."
}
```


### Server Failures
```
Scenario: Database connection failed
Response: 500 Internal Server Error

  "message": "Service temporarily unavailable. Please try again later."
}

Scenario: External API (Gemini) failed
Response: 500 Internal Server Error
{
  "message": "AI service is temporarily unavailable. Please try again later."

Scenario: Circuit breaker open
Response: 503 Service Unavailable
{
  "message": "AI service is temporarily unavailable due to rate limiting. Please try again in 2 minutes."
}
```

## 9.4 API Integration Flow

```javascript
// Example: Axios instance with JWT interceptor
const api = axios.create({
  baseURL: 'https://api.moneymanager.com',
  headers: {
    'Content-Type': 'application/json'
  }
});

// Add JWT to all requests
api.interceptors.request.use(config => {
  const token = localStorage.getItem('token');
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

// Handle 401 (redirect to login)
api.interceptors.response.use(
  response => response,
  error => {
    if (error.response?.status === 401) {
      localStorage.removeItem('token');
      window.location.href = '/login';
    }
    return Promise.reject(error);
  }
);

// Example API calls
export const dashboardApi = {
  getDashboard: () => api.get('/dashboard'),
  getAnalytics: (period) => api.get(`/api/analytics/${period}`),
};

export const transactionApi = {
  addExpense: (data) => api.post('/expences', data),
  addIncome: (data) => api.post('/incomes', data),
  deleteExpense: (id) => api.delete(`/expences/${id}`),
};

export const aiApi = {
  analyzeSpending: () => api.post('/api/ai/analyze-spending'),
  getHealthScore: (refresh = false) =>
    api.get(`/api/ai/financial-health?refresh=${refresh}`),
  askQuestion: (question) =>
    api.post('/api/ai/ask', { question }),
};
```

# 10. Advanced Notes

## 10.1 Performance Optimizations

### Database Level
| Optimization | Implementation | Impact |
|--------------|----------------|--------|
| Indexed Queries | `@Index` on frequently queried columns | Faster lookups |
| Pagination | `Pageable` for large datasets | Memory efficient |
| Batch Processing | Limit recurring transactions per job | Protect DB |
| Read-only Transactions | `@Transactional(readOnly = true)` | Connection pooling |
| Query Limiting | Max 365 days for analytics | Prevent heavy queries |

### Caching Strategy
| Cache | TTL | Purpose |
|-------|-----|---------|
| `dashboard` | 5 minutes | Frequently accessed |
| `subscription` | 1 hour | Rarely changes |
| `categories` | 24 hours | Rarely changes |
| `ai-insights` | 6 hours | Expensive to generate |
| `analytics` | 10 minutes | Changes with transactions |
| `predictions` | 6 hours | Computed data |
| `anomalies` | 30 minutes | Recent data |
| `ai-tips` | 6 hours | API cost reduction |

### API Level
| Optimization | Implementation | Benefit |
|--------------|----------------|---------|
| Rate Limiting | Guava RateLimiter for Gemini | Prevent quota exhaustion |
| Circuit Breaker | After 3 failures, block 2 min | Prevent cascading failures |
| Lazy Loading | `FetchType.LAZY` on relations | Reduce initial load |
| Response Compression | Spring Boot default gzip | Reduce bandwidth |
